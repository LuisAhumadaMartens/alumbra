# dav1d AV1 decoder

The desktop port decodes AV1 with [dav1d](https://code.videolan.org/videolan/dav1d) (BSD-2-Clause), through its own C API
and not through libavcodec (#86). The code is `Dav1dDecoder` in `penumbra/desktop/` (target `penumbra::desktop_decode`).
It shares the worker-thread, grant, flush and error behaviour of the FFmpeg decoders, which
[FFmpeg decoders](ffmpeg-decoders.md#decoder-behaviour) describes, and the decoder chain contract of
[decoder chain](decoder-chain.md).

## Candidate and ordering

`DesktopComponentFactory::GetDecoderCandidates(StreamType::kVideo)` returns `dav1d` first, ahead of the FFmpeg candidates,
with `kind = kBundledSoftware`, `output = kCpuBuffer` and the codec `kAv1`. The FFmpeg build has no AV1 decoder at all
(`ffmpeg_components_test` asserts it), so no FFmpeg path competes with dav1d. The order is still fixed in the factory, and
`Dav1dFactoryTest.IsTheFirstAv1CandidateAndSelectedByDefault` shows that `SelectDecoderCandidates` picks `dav1d` for an
AV1 stream, as ADR-0029 requires.

## Settings

`DesktopDecoderOptions` carries what the settings runtime of #327 will resolve:

| Setting | Field | Default | Meaning |
|---------|-------|---------|---------|
| `decode.video.threads` | `video_threads` | 0 | dav1d thread count, 0 to 64; 0 lets dav1d use the logical cores |
| `decode.av1.apply_film_grain` | `av1_apply_film_grain` | true | `Dav1dSettings::apply_grain` |
| `decode.av1.max_frame_delay` | `av1_max_frame_delay` | 0 | `Dav1dSettings::max_frame_delay`, 0 to 256; 0 is dav1d's automatic choice and 1 is low latency |
| none yet | `av1_operating_point` | 0 | `Dav1dSettings::operating_point`, 0 to 31, for scalable streams |

Only the highest spatial layer of a scalable stream is output (`all_layers` is off). Values outside the ranges make
`CreateDecoder` fail with `kInvalidArgument`.

## Behaviour

- **Data.** Each sample is wrapped without copying in a `Dav1dData` that keeps the `SharedBytes` alive. The sample time and
  duration travel in `Dav1dDataProps` in the stream's time base, and come back on the picture.
- **Send and get.** The decoder alternates `dav1d_send_data` and one `dav1d_get_picture`, and takes more pictures when
  `send_data` answers `DAV1D_ERR(EAGAIN)`. At the end of the stream it drains until `EAGAIN`. It never asks for a second
  picture straight after a successful one while data is flowing, because dav1d then waits for the frame threads to finish
  every frame in flight and blocks forever on a truncated frame. The corruption tests found this.
- **Configuration.** The `configOBUs` of an `av1C` record, parsed by `umbra::codec::ParseAv1C`, are sent before the first
  sample and again after every flush, because MP4 samples need not repeat the sequence header. A configuration change in
  place is accepted when the codec is the same and sends changed `configOBUs` first.
- **Flush.** `Flush` calls `dav1d_flush`, sends the `configOBUs` again and emits a grant under the new ticket. No picture
  of the old ticket follows.
- **Film grain.** dav1d applies grain to the output pictures by default. With `apply_film_grain` false the pictures are the
  grain-free reconstruction.
- **Pictures.** An 8-bit 4:2:0 picture is `kI420` and a 10-bit one is `kI010`, wrapped without copying: the planes point into
  the `Dav1dPicture`, which the frame's `storage` releases. Pictures in another layout (4:2:2, 4:4:4, monochrome) or at 12 bits
  are a fatal `kUnimplemented` error with category `kCapability`, and the capability table does not offer them. They
  become available when the renderer can show them. The colour description comes from the sequence header.
- **Errors.** Invalid data (`EINVAL`) is `kDataLoss` with a `kTransient` hint, and after any decoding error the decoder resets
  dav1d and goes on. Out of memory is `kResourceExhausted`, and other failures are `kRecreate`.

## Tests

`dav1d_decoder_test` covers:

- the libaom test vectors `av1-1-b8-01-size-16x16`, `av1-1-b8-01-size-66x66`, `av1-1-b8-04-cdfupdate` and the film grain
  vectors `av1-1-b8-23-film_grain-50` and `av1-1-b10-23-film_grain-50`, committed under `test/fixtures/decode/av1/`. The
  output equals the libaom per-frame MD5 files, and the MD5 of the whole stream equals `dav1d --muxer md5` (dav1d 1.5.2)
  with film grain on and off, for one, automatic and four threads and for a maximum frame delay of 1. The vectors come from
  <https://storage.googleapis.com/aom-test-data/> and carry the libaom licence (BSD-2-Clause and the Alliance for Open Media
  Patent License 1.0);
- an MP4 clip with an `av1C` record, generated by `test/fixtures/decode/generate.sh` with libaom, whose reference is the
  `dav1d --muxer md5` hash of the same stream;
- flush on seek, with no stale picture, frames equal to a fresh decode of the tail, and decoding that restarts on an IVF
  stream;
- presentation order and times, in-place configuration change, a codec change refused with `kUnimplemented`, and the
  unsupported 4:4:4 layout;
- 24 seeded corruptions of each of three clips, which must neither crash nor stall.

dav1d is bit exact, so the hashes are golden (ADR-0021).
